# 발견 레지스터

S0은 저장소당 **한 번**만 돈다. 그 뒤로는 큐에서 후보를 하나씩 꺼내
S1→S7→제출을 반복한다. 발견마다 폴더가 분리되므로 서로 덮어쓰지 않는다.

## 디렉터리 구조

```
cvehunt/            ← 도구. 수정하지 않는다
  ENV.md            ← 이 타겟의 환경 (BASE 브랜치, 언어, 재현 경로)
TARGET.md           ← S0 산출물. 저장소당 하나
STATE.md            ← 지금 누구 차례인지. 코디네이터가 읽는 유일한 파일
FINDINGS.md         ← 이 파일. 발견 목록과 상태
METRICS.md          ← 사이클별 측정
findings/
  001-<slug>/
    VERIFY_RESULT.md  REPRO_PLAN.md  REPRO_RESULT.md
    REPORT_DRAFT.md   LOOP_STATE.md  REVIEW.md
  002-<slug>/
    ...
```

**작업 중인 발견의 폴더만 건드린다.** 루프의 `LOOP_STATE.md`도 그 폴더 안에
있으므로 발견 #2를 진행해도 #1의 상태가 깨지지 않는다.

## 새 발견을 시작하는 절차

**1. 폴더를 만들고 번호를 부여한다**

```bash
N=001; SLUG=<짧은-영문-슬러그>
mkdir -p findings/$N-$SLUG
git add findings/$N-$SLUG && git commit -q -m "start finding $N"
```

**2. `STATE.md`를 그 발견으로 세팅한다**

```markdown
# STATE
FINDING: <N>-<slug>
STAGE: S1
NEXT: hunter
UPDATED_BY: human
UPDATED_AT: <ISO8601>
BLOCKED_REASON:
```

진입 단계는 상황에 따라 다르다:
- 큐에서 새로 파는 경우 → `S1` / `hunter`
- 이미 CONFIRMED로 올라와 있는 후보 → `S2` / `reviewer`
- 외부 모듈 유보만 남은 후보 → `S3` / `external`

**3. 커밋하고 코디네이터를 깨운다** — `cvehunt/START.md` 한 줄

## 중복 방지

발견 #2 이후는 **자기 저장소의 이전 발견과도 중복 검사**를 해야 한다.
`VERIFY.md`의 G4에 다음을 추가로 적용한다:

- `FINDINGS.md`의 기존 항목과 같은 파일·같은 파라미터인가
- 이미 제출한 어드바이저리의 수정이 이 경로도 덮는가
  (덮는다면 별건이 아니라 그 어드바이저리에 코멘트로 붙이는 게 맞다)

같은 근본 원인이면 **하나의 어드바이저리로 묶어라.** 메인테이너가 한 번에
고칠 수 있고, 쪼개서 내면 슬롭으로 보인다.

## 제출 간격

이전 어드바이저리가 아직 트리아지 중인데 다음 것을 바로 내면 부담을 준다.
가능하면 이전 건에 응답이 온 뒤 다음을 낸다. 급하지 않다면
**한 번에 하나씩**이 관계 유지에 낫다.

단, 심각도가 확연히 높거나(무인증 RCE 등) 이미 공개 노출된 건은
기다리지 말고 즉시 낸다.
